# Situation
製造業クライアント向けに、Amazon Bedrockを基盤としたRAG（Retrieval-Augmented Generation）システムを構築するプロジェクトでした。対象データは工場の運用手順書、運用実施記録（Excel）、工場のレイアウト図面・配管図（PDF）など、フォーマットが混在する大量のドキュメント群。クライアントから提供された想定QAを達成基準とし、回答精度の向上を目指しました。

# Task
パイプライン全体の設計・実装および精度検証を担当しました。技術選定に必要な調査（サービス比較、論文調査等）はインターンに任せ、その調査結果をもとにアーキテクチャ判断と実装を行いました。

主な課題は、工場の図面PDF（機器配置図、配管計装図等）をそのままBedrock Knowledge Basesに投入した場合、Bedrockの標準テキスト抽出では表構造が崩れる・注記の階層が失われる問題があり、想定QAへの回答精度が出なかったことです。Excelは自前でMarkdown変換すれば済んだが、PDFは標準パーサーでは不十分でした。

# Action
以下の技術的アプローチを実施しました。

- **Azure AI Document Intelligence（prebuilt-layout）の採用**:
  - PDFをMarkdown形式で構造化テキスト出力するモデルを採用。表はMarkdownテーブルとして、見出し・段落・注記は適切なヘッダー階層として出力される。
  - APIベースで大量PDFをバッチ処理可能。日本語対応しており、工場図面の日本語注記も処理可能。
  - LlamaParse（VLMベース）も候補に上がったが、APIの安定性・日本語処理の実績・バッチ処理のしやすさからAzure Document Intelligenceを採用。

- **前処理パイプラインの構築**:
  - S3上のPDF/Excelを入力とし、ExcelはPythonスクリプトでMarkdown変換、PDFはAzure Document Intelligence経由でMarkdown化。
  - 構造化テキストをS3に格納後、Bedrock Knowledge Basesに取り込み。メタデータ（ドキュメント種別、図面番号等）を付与。
  - ExcelもPDFも最終的にMarkdown形式に統一してからBedrockに投入し、LLMにとって検索・生成の品質を均一化。

- **Bedrock側のチューニング**:
  - チャンキング戦略：図面由来のMarkdownは情報密度が高いため、チャンクサイズをやや大きめに設定し、表が途中で分断されないよう調整。
  - メタデータフィルタリング：ドキュメント種別（drawing / procedure / record）と図面番号により、質問の種類に応じて検索対象を絞り込み。
  - プロンプトテンプレート調整：「回答時は出典ドキュメント名を明記すること」「表データに基づく回答は該当行を引用すること」を指示に追加。

- **図面がRAGで果たす役割の設計**:
  - 機器名・仕様・エリア情報など、運用手順書には書かれていない「設備のファクト」を図面から引けるよう設計。
  - 想定QA例：「〇〇エリアにある設備の一覧は？」「ポンプP-101の仕様は？」「配管L-301の接続先は？」等に対し、機器配置図・配管計装図のテキストを情報源として活用。

# Result
- **精度の改善**: 図面PDF内の機器仕様表が、Bedrock標準パーサーではセル構造が消えてフラットな文字列となり誤答が発生していたが、Azure Document Intelligence経由で表構造がMarkdownテーブルとして保持されるため、正しい列に基づいて回答できるようになった。
- **知見の獲得**: 構造化さえできれば図面はRAGの強力なソースになる一方、テキスト抽出ベースでは図面上の配置関係や図形の意味（配管の接続方向等）は扱えない限界を体感。VLM＋CVの組み合わせが必要になる領域の設計判断に活きる。
