## 1. 工場向けRAGシステムにおける図面・ドキュメントの前処理パイプライン（2024年）

### プロジェクト概要

製造業クライアント向けに、Amazon Bedrockを基盤としたRAG（Retrieval-Augmented Generation）システムを構築。対象データは工場の運用手順書、運用実施記録（Excel）、工場のレイアウト図面・配管図（PDF）など、フォーマットが混在する大量のドキュメント群。クライアントから提供された想定QAを達成基準とし、回答精度の向上を目指した。

### 自分の役割

パイプライン全体の設計・実装および精度検証を担当。技術選定に必要な調査（サービス比較、論文調査等）はインターンに任せ、その調査結果をもとに自分がアーキテクチャ判断と実装を行った。

### 課題

工場の図面PDF（機器配置図、配管計装図等）をそのままBedrock Knowledge Basesに投入した場合、Bedrockの標準テキスト抽出では**表構造が崩れる・注記の階層が失われる**問題があり、想定QAへの回答精度が出なかった。Excelは自前でMarkdown変換すれば済んだが、PDFは標準パーサーでは不十分だった。

### 採用したアプローチ

**Azure AI Document Intelligence（旧 Form Recognizer）の `prebuilt-layout` モデル**を採用。

選定理由：

- PDFを入力すると**Markdown形式で構造化テキストを出力**してくれる（2024年にGA）
- 表はMarkdownテーブルとして、見出し・段落・注記は適切なヘッダー階層として出力される
- APIベースで大量PDFをバッチ処理でき、1枚ずつ個別の前処理を行う必要がない
- 日本語対応しており、工場図面の日本語注記も処理可能

※インターンの調査ではLlamaParse（LlamaIndex提供、VLMベースのPDFパーサー）も候補に上がったが、APIの安定性・日本語処理の実績・バッチ処理のしやすさからAzure Document Intelligenceを採用した。

### パイプライン全体像

```
S3 (PDF/Excel)
  ├── Excel → Pythonスクリプトで Markdown変換
  └── PDF  → Azure Document Intelligence (prebuilt-layout) → Markdown
         ↓
  構造化テキスト (Markdown) をS3に格納
         ↓
  Bedrock Knowledge Bases に取り込み
  （メタデータ付与: ドキュメント種別、図面番号等）
         ↓
  Retrieve and Generate で回答生成
```

設計上のポイント：ExcelもPDFも最終的にMarkdown形式に統一してからBedrockに投入。LLMにとってMarkdownは最も理解しやすい構造化テキストの一つであり、ソースのフォーマットが異なっても検索・生成の品質を均一にできる。

### 図面がRAGで果たす役割

工場のPDF図面（機器配置図、配管計装図等）はCADソフトから出力されたPDFで、テキストレイヤーが埋め込まれているタイプ。図面内には機器名称（ポンプP-101、タンクT-201等）、エリア名（A棟1F、ユーティリティ室等）、仕様注記がテキストとして含まれる。

クライアントの想定QAの中で、図面データが回答に効くのは以下のような質問。

| 想定QAの例 | 回答に必要な情報源 |
|---|---|
| 「〇〇エリアにある設備の一覧は？」 | 機器配置図のテキスト（機器名・エリア名） |
| 「ポンプP-101の仕様は？」 | 図面のタイトルブロックや注記表に記載された仕様情報 |
| 「△△設備の点検時に周辺で注意すべきことは？」 | 図面から周辺機器の情報 ＋ 運用手順書の安全注意事項 |
| 「配管L-301の接続先は？」 | 配管計装図の注記・ライン番号テキスト |

図面は運用手順書には書かれていない「設備のファクト」（所在・仕様・構成）の情報源として機能した。

### 精度向上で具体的に何が改善されたか

**Before（Bedrock標準パーサーのみ）：**

図面PDF内の機器仕様表が、テキスト抽出時にセル構造が消えてフラットな文字列になる。例：`ポンプP-101 50A SUS304 冷却水 15kW P-102 80A SGP 蒸気 30kW` → どれがどの機器のどの項目かをLLMが判別できず、「ポンプP-101の材質は？」に「SGP」と誤答するケースがあった。

**After（Azure Document Intelligence経由）：**

表構造がMarkdownテーブルとして保持されるため、正しい列に基づいて回答できるようになった。

### Bedrock側の設定・チューニング

**チャンキング戦略：** 図面由来のMarkdownは通常の文書より1チャンクあたりの情報密度が高い（表1つに多数の機器情報が含まれる）ため、チャンクサイズをやや大きめに設定し、表が途中で分断されないように調整。想定QAへの回答精度を見ながらチャンクサイズとオーバーラップを調整した。

**メタデータフィルタリング：** S3格納時にドキュメント種別（drawing / procedure / record）と図面番号をメタデータとして付与。質問の種類に応じて検索対象を絞り込むことで、無関係なソースからの誤った回答を減らした。

**プロンプトテンプレートの調整：** Retrieve and Generateのプロンプトテンプレートに、「回答時は出典ドキュメント名を明記すること」「表データに基づく回答は該当行を引用すること」といった指示を追加。想定QAでの検証時に「正しいソースから正しく引けているか」を確認可能にした。

### この経験で得た知見

**「構造化さえできれば、図面はRAGの強力なソースになる」** — 機器名・仕様・エリア情報など、運用手順書には書かれていないファクトを図面から引けるようになったことで、回答の網羅性が大きく改善した。

**「テキスト抽出ベースの限界も体感した」** — Azure Document Intelligenceで表やテキスト注記は拾えたが、図面上の配置関係（「この設備のすぐ横に何があるか」）や図形の意味（配管の接続方向、バルブの開閉状態）はテキストレイヤーからは取れない。

### Civilinkとの接続

Civilinkの土木図面照査はまさに「視覚的な構造理解」が核心であり、テキストRAGだけでは解けない。VLM＋CVの組み合わせが必要になる領域。テキストベースRAGで図面を扱った経験があるからこそ、その先に何が必要かを実感を持って設計判断できる。

CivilinkがYOLOを採用している理由も、この経験から理解できる。図面全体をVLMに投げるとトークンコストが爆発し、精度も落ちる。YOLOで先に「意味のある領域（図枠、部材表、配筋詳細図等）」を切り出してから、その領域だけをVLMに渡す2段パイプラインにすることで、コスト削減と精度向上を両立できる。YOLOは照査ワークフロー全体の自動化を可能にするルーターとしての役割も担っており、自分がRAG案件でやった「ドキュメント種別によるメタデータフィルタリング」と設計思想は共通している。

## 2. Hulu推薦システム：マルチモーダルEmbeddingの設計・実装

### プロジェクト概要

Huluの推薦システムにおいて、コールドスタート問題（新規コンテンツや視聴データが少ないコンテンツの推薦精度が低い）の改善が課題。コンテンツの**説明文テキスト**と**アートワーク画像**からEmbeddingを生成し、推薦モデル（Two-Tower）の特徴量として組み込んだ。

### フェーズ1：テキストEmbedding（multilingual-e5-base）

#### モデル選定

説明文（あらすじ・キャッチコピー）のEmbeddingに**multilingual-e5-base**（Microsoft、768次元）を採用。

選定理由：

- Huluは日英両方のコンテンツを扱うため多言語対応が必須。mE5は100言語以上をサポート
- ベースアーキテクチャはXLM-RoBERTa-base。10億の多言語テキストペアで対照学習（Contrastive Pre-training）後、ラベル付きデータセットでファインチューニング済み
- テキスト検索・意味的類似性タスクに最適化されており、推薦の特徴量として「似た説明文のコンテンツを近くに配置する」用途にそのまま適合
- ゼロショットのベースライン精度が高く、追加学習の効率が良い

不採用モデル：

- `paraphrase-multilingual-mpnet-base-v2`：日本語性能がmE5より劣る
- `sonoisa/sentence-bert-base-ja-mean-tokens`：日本語特化だが英語コンテンツを扱えない
- `cl-tohoku/bert-base-japanese-v3`：文単位のEmbeddingに最適化されておらず、ベースラインが低い

#### ファインチューニング：ジャンルターゲットのメトリックラーニング

mE5の事前学習は汎用的なテキスト類似性であり、「ホラーとロマンスの説明文を分離する」というジャンル軸の最適化はされていない。ジャンルラベルをターゲットにTriplet Margin Lossでファインチューニングを行い、同ジャンルの説明文が近く、異ジャンルの説明文が遠くなるEmbedding空間を学習させた。

```python
from pytorch_metric_learning import miners, losses

miner = miners.MultiSimilarityMiner(epsilon=0.1)
loss_fn = losses.TripletMarginLoss(margin=0.3)

embeddings = model.encode(descriptions)
hard_pairs = miner(embeddings, genre_labels)
loss = loss_fn(embeddings, genre_labels, hard_pairs)
```

マルチジャンル対応：Huluのコンテンツは複数ジャンルを持つ（例：「アクション」かつ「SF」）ため、全ジャンルが完全に異なるペアのみをnegativeとして扱うロジックを実装。

#### Two-Towerモデルへの組み込み

テキストEmbedding（768次元）は事前計算済みの固定特徴量としてItem Towerに入力。

```
[User Tower]                          [Item Tower]
  視聴履歴                               ジャンル、出演者、放送年
  嗜好ジャンル                            協調フィルタリング特徴
  視聴時間帯                              テキストEmb (mE5, 768-dim)
  行動特徴                               画像Emb (CLIP, 512-dim) ※フェーズ2
    ↓                                      ↓
  FC layers                              Projection → FC layers
    ↓                                      ↓
  User Embedding (128-dim)              Item Embedding (128-dim)
    ↓                                      ↓
    └──────── cosine similarity ─────────┘
```

Item Tower内でFC層を通し128次元に射影。mE5の768次元をそのまま使わず射影する理由は、他の特徴量（メタデータ等）との次元バランスを取るためと、ANN検索（Faiss等）のコスト削減のため。

全コンテンツのEmbeddingはバッチ推論で事前生成し、オンラインサービング時にはルックアップのみ。新規コンテンツ追加時にバッチ生成を走らせる運用。

#### 効果

コールドスタート改善：視聴データが蓄積されていない新規コンテンツでも、説明文Embeddingが意味的に類似した既存コンテンツとの近傍関係を提供し、推薦の初期品質が向上。

### フェーズ2：画像Embeddingの追加（CLIP）— ローカル検証まで

#### 背景と動機

テキストEmbeddingだけでは、説明文が似ているが視覚的な雰囲気が異なるコンテンツ（例：同じ「サスペンス」でもダークトーンのクライムドラマと明るいトーンのコメディサスペンス）を区別できない課題があった。アートワーク画像には、ジャンルの雰囲気やトーンを反映する視覚的シグナルが豊富に含まれており、テキストとの補完関係が期待された。

#### CLIPの採用理由

- **画像とテキストが同一Embedding空間に載る。** CLIPは画像エンコーダ（ViT-B/32）とテキストエンコーダ（Transformer）を対照学習で同時に訓練しており、画像と説明文を同じ空間で直接比較できる
- **マルチモーダルLLMの基盤技術。** GPT-4V、LLaVA等のVLMの画像エンコーダはCLIPベース。CLIPの特性を理解することはVLM活用の土台になる
- **メトリックラーニングとの親和性。** CLIP自体が対照学習で訓練されたモデルであり、ジャンルラベルでのファインチューニングと設計思想が一貫する

#### ローカル検証で確認した内容

open_clipを用いてアートワーク画像のEmbeddingを生成し、ジャンルラベルでのメトリックラーニング（Triplet Margin Loss）による ファインチューニングをローカル環境で検証。

```python
import open_clip

model, _, preprocess = open_clip.create_model_and_transforms(
    'ViT-B-32', pretrained='laion2b_s34b_b79k'
)
tokenizer = open_clip.get_tokenizer('ViT-B-32')

# 画像Embedding（512次元）
image = preprocess(artwork_image).unsqueeze(0)
image_features = model.encode_image(image)  # (1, 512)

# テキストEmbedding（512次元）— 同一空間
text = tokenizer(["クライムサスペンスの傑作"])
text_features = model.encode_text(text)  # (1, 512)
```

検証結果として、ファインチューニング前（CLIP事前学習のまま）でも、同ジャンルのアートワークがEmbedding空間上でクラスタリングされる傾向が確認でき、ジャンルラベルでのメトリックラーニングによりさらに分離が改善されることを確認。テキストEmbeddingとの補完効果（画像で捉えられる情報とテキストで捉えられる情報の違い）も定性的に確認した。

#### 本番投入に至らなかった理由

プロジェクトのスケジュール上、フェーズ1（テキストEmbedding）の本番投入とその効果検証が優先され、フェーズ2（CLIP画像Embedding）は**ローカルでの検証とTwo-Tower組み込みの設計検討まで**で時間切れとなった。技術的な実現可能性は確認済みで、本番投入の設計（バッチ推論パイプライン、Item Towerへの統合、ANN再構築）も完了していた。

### Civilinkとの接続

#### CLIPの実務経験 = VLMの基盤理解

CLIPのファインチューニングをローカル検証レベルとはいえ実務で触ったことで、VLMが「画像をどう理解しているか」の内部構造を把握している。プロンプト設計やエラー分析時に、画像エンコーダ側の特性を意識した判断ができる。

#### マルチモーダル統合の設計経験

テキスト（mE5）と画像（CLIP）という異なるモダリティのEmbeddingを統合してプロダクトに組み込む設計を実務で行った。Civilinkの図面解析では視覚情報とテキスト注記を統合的に扱う必要があり、「どの情報はCVで捉え、どの情報はVLM/LLMで処理すべきか」の切り分け判断に直接活きる。

#### メトリックラーニングによるドメイン適応

汎用事前学習モデルをドメイン固有タスクに適応させた手法は、Civilinkで「図面の領域種別」「部材カテゴリ」をターゲットにモデルを適応させるアプローチと同じ設計パターン。

## 補足：キャッチアップ中の技術

- **CLIP**：上記の通り、Huluで実務レベルの検証経験あり。マルチモーダルLLMの基盤技術としての理解
- **DETR（Detection Transformer）**：Transformerベースの物体検出モデル。YOLOと異なりアンカーフリーでEnd-to-Endの検出が可能。図面内の領域検出における代替手法としてキャッチアップ中
